# Windows Port Plan — Ultima V Native

Branch `windows/initial-port`, worktree `../ultima-v-native-windows`, based on
`main` at `96a55ff9` ("Refine T-Deck UI fidelity"). This document records the
architecture census done before the port, the decisions taken from it, what
was built, and what remains. It is updated as the work lands; the commit
hashes of each step are in [§10 Progress log](#10-progress-log).

---

## 1. Goal and constraints

A playable, independently buildable **Windows x64** build of Ultima V Native,
using **SDL3**, with:

- ONE gameplay implementation: the shared `native/core` and the T-Deck
  application layer are compiled from the firmware's own sources, with small
  behaviour-preserving seams for the desktop (section 5); no gameplay is
  reimplemented;
- the T-Deck build and behaviour preserved (the host suite stays green; the
  firmware still compiles);
- an explicit **Original** mode (preservation, DOS keyboard, 1988 rules) and
  **Enhanced** mode (the project's existing optional enhancements);
- no copyrighted game data in the repository or the executable; assets come
  from the player's own installation;
- saves compatible with the T-Deck (and the DOS save bridge kept).

## 3. Architecture census (summary)

Nine read-only readers covered runtime, Board/display, input, storage,
resources/pack pipeline, audio, Original/Enhanced, ESP-IDF/compiler
portability and documentation. The findings that shaped the port:

**Application layer.** `tdeck::AlphaRuntime` (`native/targets/tdeck/main/alpha_runtime.{h,cpp}`)
is the whole application: it owns the game state, every core session, the
title/menus (`FrontendSession`), the System Menu, saves, audio policy and the
scene pacers, and is driven by `initialize()`, `handle(RawInputEvent)`,
`render(Board&)` and `loop_wait_ticks()`. Its direct ESP-IDF surface is small
(esp_timer, heap_caps, ESP_LOG, one FreeRTOS diagnostic). It already compiles
on a PC in ~60 host test targets, but those use a test fixture
(`attach_host_test_fixture`) — **the production `initialize()` had never run
off the device** before this port.

**Presentation.** `tdeck::Board` (`tdeck_board.cpp`, 1,813 lines) composes
every screen — title, menus, play frame, console, shops, endgame — and sends it
to the ST7789 panel as SPI windows of big-endian RGB565, redrawing only what
changed and relying on the panel to keep its contents. The host tests already
run it over a fake panel (`host_tests/board_shims/fake_tdeck_bus.cpp`), which
is a test model (timing model, unbounded instrumentation vectors) not fit to
ship.

**Input.** `RawInputEvent` is matrix-level (column/row, Sym/Alt/Shift) and
trackball pulses; `UiInputAdapter::translate` turns it into
`openu5::UiAction` / `DeviceShortcut`. Arrow keys cannot simply be fed as
trackball pulses (a speed-dependent accumulator with step gaps), and Escape
has no code (Cancel is the Mic key found by matrix position). After
translation, the runtime uses the raw event only for a log name, the
Movement-Mode source string and its timestamp.

**Storage.** All files are `"/sd/ultima5/..."` paths (ESP-IDF VFS) in
`alpha_save.cpp`, `alpha_resources.h`, `asset_pack.h`, `alpha_audio.h`,
`device_smoke_tests`; saves are two generations per slot plus a 32-byte commit
record; the device code already unlinks before rename (FATFS semantics). The
host tests redirect `/sd` with a force-included header (`sd_shims/host_sd_vfs.h`).

**Resources.** Two identity-locked packs (`openu5-assets.bin`,
`openu5-alpha1-resources.bin`: exact size + CRC checked in `main.cpp`) and an
optional audio pack. They are generated by TypeScript tooling
(`npm run extract`, a fixture generator, `pack:native`, `pack:alpha1`,
`pack:audio`); the resource pack embeds byte-exact `JSON.stringify` output, so
a C++ re-implementation of the generator would have to reproduce V8's JSON
formatting to pass the identity lock — not realistic for this port.
`native/core/src/loot.cpp` includes a git-ignored `loot_names.inc`, which is
regenerated byte-for-byte from the tracked `game/src/core/data/longEquipNames.json`.

**Audio.** The whole synth/pump/service stack is portable C++
(`openu5::AudioRingPump`, PC-speaker SFX synth, OPL2 music synth); only
`tdeck_audio.cpp` (I2S + FreeRTOS task) is device-specific. Music exists only
with the music-patched audio pack; nothing is synthesised for a stock game.

**Original / Enhanced.** There is **no mode flag** in the code. "Enhanced"
rules are the per-journey `EnhancedState` (Difficulty Original/Relaxed/Easy/Custom,
15 cheats, World toggles) stored in the save sidecar's `"enhanced"` key and
changed from the System Menu; Original = the defaults, guarded by preservation
golden tests. Several T-Deck input adaptations apply in every mode (spell
lists for Cast/Mix, list-only "Player:" prompts, Mic = Esc, WASD Movement
Mode, device key legends).

**Portability.** The core has no platform dependencies. GCC-only constructs:
five `__attribute__` sites (`perf_report.cpp` ×2, `input_controller.cpp`,
`alpha_runtime.cpp` ×2). C++20 is required (designated initialisers, `__VA_OPT__`).

## 4. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **MSVC (Visual Studio 2026, x64) is the primary toolchain**; CMake; C++20; static CRT (`/MT`) | requested; the core needed one two-line fix; a static CRT means no VC++ redistributable for players |
| D2 | **SDL3 3.4.16**, fetched by CMake `FetchContent` from the official release tarball, **pinned by SHA-256**; `UV_USE_SYSTEM_SDL3` / `FETCHCONTENT_SOURCE_DIR_SDL3` for installed or offline copies | reproducible, no package manager for builders or players |

### Presentation (Classic Framed)

`src/app/presentation_layout.{h,cpp}` (pure, unit-tested) computes every
frame; SDL's logical presentation is off, so there is no float centring.

- **Picture**: `u = max(1, min(W div 320, H div 240))` of the renderer's
  output; origin `((W−320u) div 2, (H−240u) div 2)` — an odd leftover pixel
  goes right/bottom, deterministically. Nearest sampling.
- **Ring** (Framed), outward: 4u black (the Board's own 4 px from glass to
  play window), 1u white rule (`kChromeRule` 0xFFFF), 2u band (`kChromeBand`
  0x0015, band-outside-rule as the shell frames its menus), its outer corners
  cut 2u/1u like `kCornerCutSmall`. Full ring when both margins hold 7u;
  the two side pillars (full height) when only the width does; nothing
  otherwise (4:3 and 5:4 screens, outputs under 320×240). Each colour is a
  1×1 RGB565 texture stretched whole, so the band is the in-game band's
  exact screen colour on any renderer (D3D11 keeps B5G6R5; a draw colour
  shows 0x0000AC beside the picture's 0x0000AD there). The first build used
  one texel of a 2×1 atlas: on D3D11 the last 2–4 px of every band row
  sampled the white texel (review finding; a source rectangle inside the
  texel is no fix, the software renderer truncates it to nothing).
- **Fit**: the largest 4:3 rectangle, `SDL_SCALEMODE_PIXELART` when the
  scale is fractional (SDL 3.4). On D3D11 that is a pixel-sized box filter:
  even pixels with a one-pixel blend at each texel edge, so Fit is the one
  mode that is not pixel-exact; software and D3D9 treat it as nearest
  (uneven pixels). `expect window_layout` accepts a fractional-Fit pixel
  that is a blend of the 3×3 texels around it; `expect picture_sampling`
  pins the sampler, which the software renderer cannot show in pixels.
- **Window N×**: client (320+16)N × (240+16)N in Framed when the window
  (client + `SDL_GetWindowBordersSize`) fits the display's usable bounds,
  else 320N × 240N, else N−1; centred with its whole frame inside the work
  area (title bar never above it); aspect locked for dragging (21:16 / 4:3);
  restored from maximised first. Ctrl+= / Ctrl+- and the Display row step
  1× .. the largest that fits. A normal window's N follows a drag or a snap
  (`max(1, min(w div 320, h div 240))`), so the Display row and Ctrl+= / -
  start from the picture the player sees; that N is shown, never saved.
  A Scaling change resizes only when the window's shape changes (framed ↔
  bare): the new mode's Window N× around the old centre, inside the work
  area; Whole pixels ↔ Fit keeps size and place. While fullscreen or
  maximised (Windows ignores sizes then) the new shape waits until the
  window is a normal window again (leaving fullscreen, or
  `SDL_EVENT_WINDOW_RESTORED`). No `"windowScale"` = automatic:
  `floor(3 × display content scale)` within what fits, re-derived on
  `SDL_EVENT_WINDOW_DISPLAY_SCALE_CHANGED` and not written until the player
  picks a scale; a scale reduced at start-up (saved on a bigger display) is
  shown as reduced but kept in `windows.json` until the player changes it.
  `windows.json` always holds the player's last choice (as the window got
  it), or nothing for the automatic scale.
- **Measured** (the real exe's frames read back headless, 2c8de821 vs
  `windows/presentation-wip`): 1920×1080 — before, 4× picture 1280×960 at
  320,60 = 59.3 % of the screen, 844,800 px (40.7 %) black letterbox with no
  edge; Framed, the same picture, ring 55,680 px (2.69 %), black 38.1 %;
  Fit 1440×1080 = 75.0 %. 2560×1440 — 6× = 75 %, pillars 51,840 px.
  1366×768 — 3× = 65.9 %, full ring 31,320 px. Default window 960×720
  bare → 1008×768 framed (picture 89.3 %). The research's 1440×1080 / "4×
  with bands at 150 %" hypothesis does not occur on Windows (SDL window
  coordinates are physical pixels); the real DPI effect was a physically
  smaller window, now handled by the automatic scale.
- **Not done**: a Desktop Adaptive layout (a 480×270-class canvas with the
  status box and context bar under the map and a 49-column console) needs a
  `BoardLayout` in the shared Board, runtime panel sizes and new goldens; it
  was mocked up from real captures only.

## 6. What works (and how it was verified)

**Automatically verified** (by the tests below, on this machine):

- Build: MSVC 14.51 (Visual Studio 2026), x64, Release, warnings-as-errors on
  the Windows sources; SDL3 3.4.16 from the pinned source release; static CRT
  — the executable depends only on `SDL3.dll` and Windows system DLLs.
- Start-up and shutdown: the real `AlphaRuntime::initialize()` with the
  identity-locked packs, the title, clean exit (every scenario).
- Presentation: the firmware's own Board on the virtual ST7789 (title, menus,
  character creation, play frame, console, Developer screen); the decoder is
  unit-tested and the real Board draws deterministically.
- Keyboard: the complete desktop key map in both interface modes (443 checks,
  including AltGr as SDL3 sends it and the 1988 "Player:" highlight), routed
  through `AlphaRuntime::handle_action()`.
- Title/menus, character creation, play, Look/Talk prompts, a town, a dungeon
  (walk/turn/ignite), a surface fight (arena opens, attack), typed spell names
  and the list in Enhanced, a typed cast in an arena ("Cast..." first and
  once, a refused name ends the turn), (Q)uit & Save (RETURN/ESC ignored),
  System Menu save/load, F5/F9 quick save/load, the Original-mode key rules,
  the interface-mode switch and its persistence, the presented window
  (18 scenarios of the real executable, plus the opt-in Direct3D 11 window
  scenario).
- Original mode's 1988 interaction model (D22-D24): the roster picker for
  Cast/Ready/Z-stats/New Order/Camp, `Player:` / `Spell name:` / `Item:` /
  `Status:` rows, ESC/RETURN/Space rules at text, Y/N and getdir prompts,
  `What?`, the arena's turn endings, the camp's questions; Enhanced keeps its
  panels and bars (`scenario_original_interface`, `_arena`, `_camp`,
  `_typed_cast_original`, `scenario_enhanced_interface`; host
  `win_dos_interface` 95 checks, `win_dos_runtime` 19 pixel checks).
- Saves: real `alpha_save.cpp` through the `/sd` mount (slot files, commit
  record layout = the T-Deck's 32 bytes), save/load round trips; the PC/DOS
  bridge imports an original `SAVED.GAM`/`SAVED.OOL` into Slot 1 and exports
  `export\slot1\SAVED.GAM` (4,192 B) / `SAVED.OOL` (512 B) / `EXPORT.TXT`.
- Storage: FATFS rename semantics, `fsync` → `_commit`, non-ASCII data paths.
- Audio: the SDL3 backend renders exactly what the core `SfxPlayer` renders;

## 8. Known limitations and risks

- Development build: not yet played end to end by a person on Windows.
- Making the packs needs Node.js (or a prepared T-Deck SD card).
- Tracked core sources compile short verbatim game strings into every build
  (`shop_greetings.inc`, `shop_tables.inc`, `gem_category.inc`, the equipment
  names); the asset-preparation bundle embeds the tracked repository JSON it
  needs. Both are pre-existing project content and also true of the published
  T-Deck firmware; flagged for the owner, not changed by the port.
- The Windows build shows the T-Deck's screen layout; some long list footers
  were written for that width.
- `native/core/tools/a4_ui4_mutation_check.py` mutation F4 anchors on a
  System Menu footer literal that had already changed before this port
  (A4-POLISH3); it was stale before and is not repaired here. The anchors the
  port itself moved (A4-POLISH3 M11, A4-ENH1 K3/D1) are repaired.
- A spell the location forbids (with some mixed) still asks for its target
  before "Not here!" -- in the typed path as in the T-Deck's list path (a
  pre-existing order; CAST.OVL tests the location first). Outside an arena a
  typed "None!" / "No effect!" spends no turn; only the arena's turn rule was
  checked against the binary.
- The rules carry the project's documented, non-blocking differences from the
  1988 game (the preservation ledgers); the port adds none.
- Original mode's remaining interaction differences from 1988 are listed in
  `ORIGINAL_MODE_FIDELITY.md` §7: world turn costs (shared core), shop offers
  in a panel instead of console lines, arena J/P/Y, line and charm spell
  targeting, the dungeon's Look, the 22-column console, and the "Select:"
  placement. Each needs a shared-core or presenter change and is recorded,
  not approximated silently.
